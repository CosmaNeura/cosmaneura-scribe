# One-use desktop admission token for an empty initial window

Tier 2: intermediate desktop authentication freshness and the trusted main/native boundary. The owner approved the exact desktop assessment for source implementation and local synthetic validation only. This decision supplies no publication, deployment, account, physical-audio or configuration authorization.

Desktop preparation currently performs a fresh admission and a separate fresh Clerk mint for WINDOW. The latter measured 441–1014 ms in three correctly associated virtual samples; removing its mint leaves the original receiver HTTP request and all WINDOW mutations intact. These samples and fake-wire call counts establish neither a physical five-second start nor a guaranteed saving.

Keep the successful admission JWT only in native RAM, in a separate desktop ticket. Native validates the complete original desktop admission/preparation receipt, appointment, current native identity including session, revision, account digest and mounted workspace/binding/recovery scope. Desktop does not carry an explicit native tenant ID, so none is inferred; current tenant and all provider/session/consent/key/ownership checks remain at the existing backend mutations. The phone proof/context and default initializer behavior remain unchanged.

Fix the dispatch deadline once at admission to the earliest original mint completion plus five seconds, original checked_at plus its existing thirty-second freshness bound, and JWT expiry. Conservative monotonic conversions and wall/monotonic checks cannot renew that deadline. Expiry erases unused RAM. It limits a dispatch, not a successfully dispatched reply's lifetime.

The trusted desktop factory already owns encrypted journals, key custody, flow, coverage and queue. It issues an opaque identity proof only after clean new consent/admission and session journal saves, a new recording-input save, absence of retained flow/preparation/key/coverage/reservation/queue data, created review, new session-specific key wrapping/insertion, and a complete durable initial WINDOW recipe. Completed-then-thrown writes retain their exact data for recovery and cannot issue fresh eligibility. The opaque proof has no serialized properties; copies, casts, prototypes and renderer values cannot reproduce its WeakMap identity.

Main consumes that proof before dispatch. The separate private helper method claims its native ticket before validation, recovery or another await. It matches the complete original admission key/nonce/receipt and exact new mixed-channel thirty-reservation operation, key version, wrapped DEK and distinct saved operation/component keys. Scheduling expiry or an ineligible ticket before I/O selects one original fresh mint. A dispatched, cancelled or unknown result never causes an automatic replacement request. Recovery preserves the exact existing DEK and recipe and uses fresh credentials.

Cancellation, signout/account/revision/identity change, mount/workspace/binding/recovery change, closure, new admission or unrelated generic work invalidates eligibility. A private main/helper abandon command clears an idle or in-flight ticket when existing JS request cancellation retires its reply; it changes no receiver wire or durable schema. Original response/current-identity/epoch fences remain before publication. Generic renderer Core IPC still excludes WINDOW and receives no proof or alternate method.

The baseline admission envelope does not require the optional status/configuration extension. Mandatory admission scope, nonce, appointment, session, timestamp and preparation-key/capability validation still reject invalid replies. A valid legacy or incomplete optional extension publishes its original admission reply and declines ticket retention; the ensuing WINDOW uses fresh authorization. Missing optional fields cannot hide an invalid mandatory nonce or key.

Every SOURCE, fallback, resume, renewal, upload, clinical read and recovery keeps fresh authorization. Remote Clerk-only revocation after admission may create unused encrypted-key/lease/reservation metadata during the bounded interval. WINDOW therefore does not observe revocation identically to its former extra mint. The next fresh SOURCE still fails before hardware/audio; this residual is explicitly tested and is not a claim of instantaneous remote revocation for bearer tokens.

No receiver contract, server policy, consent state, custody format, schema, dependency, identity, account configuration or phone behavior changes. Bridge and standalone connection copies remain identical. The [flight plan](../flight-plans/2026-10-14-desktop-initial-window-token.md) records final-source synthetic checks, independent review and data-preserving recovery.
